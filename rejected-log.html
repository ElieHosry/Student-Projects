VR Boxing Match · assessed 2026-07-05 · rejection type (a) — fails module core requirements

Proposal: A VR fighting game where 2 players fight each other in a boxing match, using VR controllers, in a 3D scene with fully animated characters.

Reason: The proposal is built on requirements the module excludes. (1) VR hardware is not a target platform — the module targets Native PC, Native mobile, and web browser on mobile (see Introduction / Appendix F); VR headsets and controllers require OpenXR integration, stereo rendering and 90 Hz frame budgets that the low-level-library constraint (bare SDL2/OpenGL, no engines) puts far beyond a second-year team. (2) 3D with fully animated characters is mandatory to the concept, while the module allows 3D only as an optional extra for strong students — "graphical output mostly 2D". The core promise cannot survive without both, so this is a module-fit failure, not a category mismatch.

Nearest category & resubmission path: Games. Reshape as a 2D fighting/boxing game — side-view ring, sprite-animated fighters, deterministic fixed-tick combat loop (hitboxes, stamina, knockdowns), local 2-player on one device or networked 1v1 (Games pool M1 G11 / M2 G7), fight editor as the custom tool, and the category's Replay System purple requirement is a natural fit (round replays, KO highlights). That version would likely assess as ✅ Fit.

Drink Health Scanner · assessed 2026-07-06 · rejection type (a) — fails module core requirements

Proposal: A mobile app that uses the camera to recognize a juice/drink bottle's brand and category, then shows the user health facts about that drink, fetched from online resources through a local LLM model.

Reason: The load-bearing technology is the wrong kind for this module. (1) Brand/category recognition realistically means running a pretrained vision model, and the "local LLM" delegates the product's substance to another pretrained black box — the same failure mode as "Firebase swallows the backend": the students' C++ becomes inference glue, not engineered core technology, and pretrained ML stacks are not in the spirit of the low-level-libraries constraint (SDL2/OpenGL/FMOD/ImGui/FreeType, built-by-you engineering). (2) With recognition and content generation delegated, the real-time C++ simulation loop is decorative, the 2D graphical output is a standard mobile UI (camera view + info cards), and there is no natural custom tool. (3) Architectural confusion aside ("fetched from online resources, through a local LLM"), LLM-generated health claims are also a correctness liability no curated data source would carry.

Nearest category & resubmission path: Education + Training. Reshape as a nutrition education app with a custom-built scanner: implement EAN-13 barcode decoding from live camera frames in C++ — classic image processing (thresholding, scanline decoding) that students can genuinely build, making the per-frame camera pipeline a load-bearing real-time loop; look the product up in a curated nutrition database (data-driven architecture, no LLM, no invented health claims); wrap it in lessons/quizzes about sugar content and nutrition (the education engine); and build a teacher/content editor for facts, quizzes, and product entries (the custom tool, M2 G2). Firebase syncs content and progress. Platform fit: Native mobile on the reference phone (Pixel 8a/9a) — the camera requirement makes it native by necessity. That version would likely assess as 🔶 Fit with adjustments.
